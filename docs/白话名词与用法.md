# 白话名词与用法

给非开发同事看：页面和口头里的黑话，换成能听懂的名字。更细的启动步骤、Docker、健康检查见 [`使用手册.md`](./使用手册.md)。

工作台默认：**http://127.0.0.1:5173/**（任务页）。这是一套**先教后用的空引擎**，不预置公路 / 水利 / 房建规则。

---

## 1. 黑话对照

| 页面上 / 口头说的 | 人话 |
| --- | --- |
| **夹具** | 系统自带的**演示样例**。不是工地真文件，用来让你点几下就能看到「对的一份、错的一份」。 |
| **重置演示** | 清空当前演示数据，重新种下那套样例（项目、规则本、请假条款、两份任务）。 |
| **Job / 任务** | 你上传的**一份资料**（一张图或一份 PDF）从进系统到检查完的整件事。 |
| **规范包** | 这个项目自己的**规则本**：模板、检查规则、引用的标准都装在这里。空的，要你自己教。 |
| **模板 / 框选 / FieldBox** | 告诉引擎「编号在表的哪一格、日期在哪一格」。像教它认表格。 |
| **DSL / 规则** | 写死的检查条件，例如「编号必填」「日期 A 不能晚于日期 B」。不是聊天编出来的。 |
| **正例 / 反例** | 发布规则前必须先喂两份样例：**该过的要过、该拦的要拦**，证明规则没写反。 |
| **Finding / 检查结果** | 这一条规则对这份资料的结论：过了还是没过。 |
| **blocking / 硬拦** | 这条不过就不能当自动合格。 |
| **Proposal / 待审** | **人要拍板的软意见**（措辞好不好、签没签）。还没算正式入库。 |
| **Receipt / 回执** | 中台盖的章。**没这张回执，就不算正式写进账本。** |
| **标准库** | 你们自己上传的**规范原文**（条款、表格）。用来查「这句话对应哪一条」，不是用来代替上面的硬规则。 |
| **入库 / 摄入** | 把规范文本或 PDF **拆成一条条条款，存进库里**。 |
| **处理一页 / tick** | 大 PDF **一次只处理一页**（识别文字、建索引）。失败会标「这一页识别失败 / 入库失败」。 |
| **生效版** | 当前项目**准用的那一版**规范。废止版不能当现行依据。 |
| **RAG / 检索** | 用问句或条款号去**找原文在哪**。只定位，不替你立法。 |
| **出处（file_name / 页 / unit_id）** | 命中必须能指回：**哪个文件、第几页、哪一块**（条款或表格的身份证）。 |
| **clause_id** | 条款编号在系统里的身份证。表格本身不是条款，所以表格命中这一栏显示「—」。 |
| **图边（CITES 等）** | 条款之间的关系：引用、替代、属于、支撑。用来查「被哪版替代了」。 |
| **组卷** | **按你们的分组（标段、工序）排目录预览**。这里只看，不提交。 |
| **审计 / trace_id** | 这一份资料从头到尾的**流水号**。用它把上传、检查、待审串起来对账。 |
| **右侧对话 / 本步对话 / HITL** | 就当前这一步问问「为什么拦、下一步做什么」。**聊天改不了任务状态，也写不进正式库。** |
| **内存演示 / memory** | 跑在电脑里的**临时演示库**，关开发服务后数据就没了。 |
| **live / 三库** | 接到本机 PostgreSQL + Qdrant + Neo4j（正式一点的账本和检索）。真上传还要对象存储 MinIO。 |

关系边常用英文，含义如下：

| 边类型 | 人话 |
| --- | --- |
| `CITES` | 这条引用了那条 |
| `SUPERSEDES` | 这版替代了旧版 |
| `APPLIES_TO` | 适用于 |
| `REQUIRES` | 依赖 / 必须以某条为前提 |
| `PARENT_OF` | 父条包含子条 |
| `BELONGS_TO` | 表或附件属于某条 |
| `SUPPORTS` | 表格支撑某条（靠表题或单元格里的条款号，禁止「离谁近就算谁」） |

## 2. 这东西是干什么的

配置人员先**教**引擎（项目、空规则本、表格框、硬规则、标准原文），操作人员再**用**它跑一份份资料，审核人员**认**软意见。验收看的是「能不能被教」，不是「某个专业管得对不对」。

```
教                              用                         认
建项目 / 空规则本            上传一份资料                 改措辞、确认待签
在表上框字段     ──────►    抽字段 → 硬规则检查  ──►   确认后才出回执
写规则并发布                    排目录预览（不提交）
把规范拆条入库并检索
                                 全程同一条流水号 → 审计
```

---

## 3. 五分钟看成果（演示样例已种好时）

1. 打开 [任务页](http://127.0.0.1:5173/jobs)。应有两份演示样例：日期正常的一份、日期填反的一份。
2. 点填反那条的「检查结果」：日期规则应被硬拦。
3. 打开顶栏「标准库」，检索框输入 `1.1`。命中应能指回哪个文件、第几页、哪一块。
4. 「待审」看人要拍板的措辞；「组卷」只看目录；点流水号进「审计」。
5. 右侧对话可以问「这是什么」，但**不会**改任务状态。

任务页上的「重置演示」会重新种样例。不要把几十 MB 的规范全书丢进任务上传。

## 4. 真用时怎么走（教 → 用）

**配置人员**

1. **项目**：新建项目 + 空规则本（自己起名，不要写公路/水利/房建）。
2. **模板**：在空白表上框出字段并保存。
3. **规则**：写检查条件。必须先跑通一份该过的、一份该拦的，才能发布。
4. **标准库**：
   - 短文本：改文本框 →「入库条款」→「绑定生效版」。
   - PDF：选文件（先登记待处理页）→ 反复点「处理一页」。
   - 可选：加上引用 / 替代等关系。
   - 用问句或条款号检索；聊天不得手写条款号。

**操作 / 审核人员**

5. **任务**：选资料类型（必要时再选模板），上传 JPEG / PNG / PDF，**单文件 ≤ 4MB**。
6. **检查结果**：看过了还是没过。被硬拦的不能当自动合格。
7. **待审**：改措辞或确认待签；确认后才出回执。
8. **组卷 / 审计**：按分组看目录；用同一条流水号对账。

---

## 5. 不要踩的坑

- 任务上传不是规范入库口。大 PDF 只走标准库「一次一页」。
- 没有回执，就不算正式写进账本。对对话说「确认 / 发布 / 提交」无效，要点页面按钮。
- 组卷不能提交，按钮是灰的，这是产品范围，不是坏了。
- 内存演示下重启开发服务，数据会没；再点「重置演示」。
- 接了三库但没配对象存储时：演示样例还能跑，真上传会失败（不会偷偷用假识别）。
- 引擎故意没有行业规范包。

| 顶栏 | 你在干什么 |

| 审计 | 用流水号把全过程对上账 |
